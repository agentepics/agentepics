---
title: "What are epics?"
description: "Agent Epics extend skills with durable state, enabling reusable workflows, autonomous operation, and installed capabilities."
---

At its core, an epic is a skill that remembers and stays in play. It pairs a
`SKILL.md` file (routing and instructions) with an `EPIC.md` file (stateful
workflow context), letting an agent carry forward durable state instead of
starting from scratch each session.

An epic is also a durable state container. It can hold current facts, open
work, recent history, and automation rules for a project, workflow, or
installed capability in one portable file set.

That means an epic is not just a task that takes longer. An epic can be a
reusable workflow, an autonomous operating loop with policy and hooks, or a
capability the agent keeps installed indefinitely, such as memory,
monitoring, or an integration.

It can also support several operating modes around the same shared state:
tactical work in `runtime/plans/`, recurring jobs in `cron.d/`, continuous
durable state in `runtime/state.json` or `runtime/state/`, and event-triggered
reactions in `hooks/`.

[Why state and reuse matter](/stateful-and-reusable), which compares epics
against plain skills with detailed website, book, and feature-film examples.

If you want to see one complete epic in motion, read

```directory
my-epic/
├── SKILL.md          # Required: routing + instructions (standard skill)
├── EPIC.md           # Required: workflow definition + identity
├── runtime/          # Optional: live, clearable state for the current run
│   ├── plans/        # Tactical plans (what to do now)
│   ├── state.json    # Structured machine-readable state
│   ├── log/          # Append-only activity history
│   ├── ROADMAP.md    # Long-term goals and milestones for this run
│   ├── DECISIONS.md  # Curated decision records for this run
│   └── artifacts/    # Produced outputs and deliverables
├── hooks/            # Optional: event-triggered actions
├── cron.d/           # Optional: recurring task definitions
├── policy.yml        # Optional: autonomous-operation constraints
├── skills/           # Optional: epic-scoped skills
├── scripts/          # Inherited from skill standard
├── references/       # Inherited from skill standard
└── assets/           # Inherited from skill standard
```

Every epic is a valid skill. Skill loaders that don't understand epics will
still discover and activate the `SKILL.md` file normally. Epic-aware loaders
detect the `EPIC.md` file and unlock a durable operating surface for the
agent.

## How epics work

Epics use **progressive disclosure** across 6 levels to manage context efficiently:

1. **Discovery**: The agent loads only the `SKILL.md` name and description, the same mechanism used for ordinary skills.

2. **Activation**: When the task matches, the agent reads the full `SKILL.md` body, `EPIC.md`, and `policy.yml` if present.

3. **State loading**: The agent reads structured state (`runtime/state.json` or `runtime/state/core.json`) and the current plan from `runtime/plans/`.

4. **Session continuity**: Recent `runtime/log/` entries (last 3-5) are loaded to understand what happened previously.

5. **Strategic context**: `runtime/ROADMAP.md` and `runtime/DECISIONS.md` are loaded when the agent needs long-term direction or decision history.

6. **Deep reference**: Full logs, epic-scoped skills, references, and supporting files are loaded on demand.

This layered approach keeps agents fast while giving them access to as much
context as they need, whether the epic is a project to resume, a workflow to
reuse, a capability to keep installed, or a state container coordinating
several ongoing workstreams.

## The EPIC.md file

`EPIC.md` contains YAML frontmatter with identity fields and a Markdown body describing the workflow:

```mdx
---
spec_version: 0.5.1
id: saas-launch
tags: [saas, launch, product]
timezone: UTC
---

# SaaS Launch

## Purpose
Take a product from architecture to first paying customer.

## Phases
1. Architecture decisions
2. Core implementation
3. Beta program
4. First customer onboarding

## Resume
Read the current plan in runtime/plans/ and recent runtime/log/ entries to pick up where we left off.
```

The frontmatter requires `id` (a unique identifier within the workspace) and
`spec_version` (which revision of the standard the epic targets). The body
defines the workflow's purpose, phases, success criteria, and how to resume or
operate it over time.

## Epic archetypes

Epics fall into three broad patterns:

- **Workflow epics** define a reusable process. The workflow definition stays
  stable while instance state changes each session. Example: a product launch
  checklist that can be instantiated for each new launch.

- **Instance epics** are one-off efforts with unique scope. The `EPIC.md` body
  describes the specific project rather than a generic workflow. Example: a Q1
  marketing campaign.

- **Capability epics** extend the agent itself with a durable capability or
  integration. The agent works with the epic as an installed feature rather
  than something to “finish.” Example: a memory system that persists across
  conversations.
