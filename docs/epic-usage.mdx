This page is about **using** an epic after it has been authored.

Creation defines the reusable operating model. Usage is where that model
accumulates live working state inside `runtime/`: current plans,
machine-readable facts, logs, artifacts, and eventually runtime behavior.

During usage, these operating files are typically created or updated by the
agent as the work unfolds. This page describes what that evolution looks like.

If you have not created the reusable definition yet, start with
[Epic creation](/epic-creation/getting-started).

## The first usage layer: plans

Most epics first become practically useful when the agent materializes a current
plan.

Plans are the tactical layer:

- what to do now
- what comes next
- what is blocked

```directory
saas-launch/
├── SKILL.md
├── EPIC.md
└── runtime/
    └── plans/
        └── 001-initial.md
```

```markdown
# Initial Launch Plan

Updated: 2026-03-06

## Now
- Choose the primary database
- Define the API schema for core resources
- Set up the project repository structure

## Next
- Implement authentication
- Set up CI/CD
- Prepare beta onboarding materials

## Blocked
- (nothing currently blocked)
```

Every plan file must include:

- a title heading
- an `Updated:` line
- `## Now`
- `## Next`
- `## Blocked`

This is the simplest way for the agent to keep the epic executable across
sessions.

## The next usage layer: structured state

When the epic needs facts that should be updated as data, not rediscovered from
prose, the agent will typically maintain `state.json` or `state/`.

Good candidates:

- current milestone
- active plan filename
- approval status
- budget status
- chapter status
- release status

```directory
saas-launch/
├── SKILL.md
├── EPIC.md
└── runtime/
    ├── plans/
    │   └── 001-initial.md
    └── state.json
```

```json
{
  "state_version": 1,
  "status": "active",
  "current_plan": "001-initial.md",
  "milestone": "architecture",
  "blocked": false
}
```

Reserved fields:

| Field | Purpose |
|-------|---------|
| `state_version` | Schema version, default `1` if absent |
| `status` | `active`, `paused`, `complete`, or `abandoned` |
| `current_plan` | Filename of the active plan in `runtime/plans/` |

If the state grows larger, the agent or supporting tooling may split it into a
`runtime/state/` directory and keep reserved fields in `runtime/state/core.json`.

State is what makes an epic a durable container rather than just a set of
instructions.

## The continuity layer: logs

When the epic needs durable history across sessions, collaborators, or
autonomous runs, the agent appends log entries in `runtime/log/`.

```directory
saas-launch/
├── SKILL.md
├── EPIC.md
└── runtime/
    ├── plans/
    │   └── 001-initial.md
    ├── state.json
    └── log/
        └── 2026-03-06T10-00-00Z-agent-initial-setup.md
```

```markdown
---
actor: agent
type: work
epic: saas-launch
duration_minutes: 15
---

## Initial setup

Created the first epic files and wrote the initial launch plan.

### Changes
- Added `runtime/plans/001-initial.md`
- Added `runtime/state.json`

### Next
- Start architecture decisions from the current plan
```

Filename format:

`YYYY-MM-DDTHH-MM-SSZ-{actor}-{slug}.md`

Logs are append-only. They preserve what happened, why it changed, and how the
next session should pick up.

## The operating baseline

A strong operating baseline usually looks like this:

```directory
saas-launch/
├── SKILL.md
├── EPIC.md
└── runtime/
    ├── plans/
    │   └── 001-initial.md
    ├── state.json
    └── log/
        └── 2026-03-06T10-00-00Z-agent-initial-setup.md
```

That is enough for durable multi-session work.

## When usage turns into runtime evolution

Some epics remain mostly interactive. Others evolve into active operating
surfaces.

That usually happens when the epic gains one or more of:

- `hooks/` for event-triggered actions
- `cron.d/` for recurring work
- `policy.yml` for hard autonomy constraints

Examples:

- prepare a briefing automatically when a meeting starts
- run a health or readiness check every morning
- prevent the epic from taking certain actions without escalation

At that point the epic is no longer just being resumed. It is beginning to
operate continuously or reactively around its own durable state.

## A useful mental model

Creation defines:

- what this epic is
- what phases it moves through
- what supports each phase needs
- what remains reusable across runs

Usage evolves:

- what plan is active now
- what structured facts are true now
- what happened recently
- what the agent should run automatically now

That live layer can be reset by clearing `runtime/`, which returns the epic to
its reusable definition.

That split keeps the docs clean and keeps the reader from confusing the epic
definition with the epic's live working state.
