This page is about what happens after an epic is authored.

Creation defines the reusable operating model. Usage is when the agent starts
materializing live files inside `runtime/` so the work can continue across
sessions.

## The usual growth path

Most epics become useful in this order:

1. a current plan
2. structured state
3. durable logs
4. strategic files such as roadmap and decisions
5. optional scripting behavior

Not every epic needs all five layers.

## Layer 1: plans

The first live file is usually the current plan.

```directory
saas-launch/
├── SKILL.md
├── EPIC.md
└── runtime/
    └── plans/
        └── 001-initial.md
```

```markdown
# Initial Launch Plan

Updated: 2026-03-06

## Now
- Choose the primary database
- Define the API schema for core resources

## Next
- Implement authentication
- Set up CI/CD

## Blocked
- (nothing currently blocked)
```

Plans are the tactical layer: what to do now, what comes next, and what is
blocked.

## Layer 2: structured state

Once the epic needs facts that should be updated as data instead of rediscovered
from prose, the agent usually adds `state.json` or `state/`.

```json
{
  "state_version": 1,
  "status": "active",
  "current_plan": "001-initial.md",
  "milestone": "architecture",
  "blocked": false
}
```

Good candidates for structured state:

- current milestone
- active plan filename
- approval status
- release status
- budget or risk flags

## Layer 3: logs

When continuity matters across sessions, collaborators, or autonomous runs, the
agent starts appending log entries in `runtime/log/`.

```markdown
---
actor: agent
type: work
epic: saas-launch
duration_minutes: 15
---

## Initial setup

Created the first epic files and wrote the initial launch plan.

### Changes
- Added `runtime/plans/001-initial.md`
- Added `runtime/state.json`

### Next
- Start architecture decisions from the current plan
```

Logs are the durable answer to "what happened recently?"

## Layer 4: roadmap and decisions

As the work gets longer-lived, the epic often grows two lower-churn files:

- `runtime/ROADMAP.md` for milestones and long-range intent
- `runtime/DECISIONS.md` for significant accepted decisions

These files keep strategic context out of the day-to-day plan and out of long
log history.

## Layer 5: scripting behavior

Some epics stop at plans, state, and logs. Others also add:

- `hooks/` for event-triggered behavior
- `cron.d/` for recurring jobs
- `policy.yml` for hard constraints

That is the point where the epic starts acting less like a saved project state
and more like an operating system for ongoing work.

## A useful mental model

- `EPIC.md` says what this epic is for.
- `runtime/plans/` says what matters now.
- `runtime/state.json` says what is true right now.
- `runtime/log/` says what happened.
- `runtime/ROADMAP.md` and `runtime/DECISIONS.md` say where the work is headed
  and why key choices were made.
