This guide is for builders of coding AI agents and harnesses.

The key design question is simple: how much EPIC support do you want to ship?
You do not need full scripting support on day one to be usefully EPIC-aware.

## Minimum viable support

If you only do five things, do these:

1. Discover directories that contain both `SKILL.md` and `EPIC.md`.
2. Tell the model which epics exist without loading them fully.
3. Activate an epic with progressive disclosure instead of dumping the whole
   directory into context.
4. Let the agent read and update `runtime/` files.
5. Resume from state, current plan, and recent logs.

That is enough for strong interactive EPIC support.

## Full support

Full support adds:

- `hooks/`
- `cron.d/`
- `policy.yml`
- explicit handling for unsupported scripting features

If you support these features, you must execute them according to the scripting
reference or surface that they are unsupported.

## Step 1: discover epics

At session startup, scan your configured skill locations for directories that
contain:

- `SKILL.md`
- `EPIC.md`

If you also support plain skills, treat them as a separate discovery class:

- `SKILL.md` only => plain skill
- `SKILL.md` + `EPIC.md` => epic

Typical scan locations for a coding harness:

| Scope | Path |
|-------|------|
| Project | `<repo>/.agents/skills/` |
| Project | `<repo>/.<your-client>/skills/` |
| User | `~/.agents/skills/` |
| User | `~/.<your-client>/skills/` |

## Step 2: build a lightweight catalog

At startup, disclose only the metadata the model needs to know what epics
exist.

At minimum, each epic record should include:

| Field | Purpose |
|-------|---------|
| `name` | Activation label from `SKILL.md` |
| `description` | Discovery description from `SKILL.md` |
| `location` | Path to `SKILL.md` or the epic root |
| `epic_id` | Durable identifier from `EPIC.md` |

Optional but useful:

| Field | Purpose |
|-------|---------|
| `runtime_features` | Whether `hooks/`, `cron.d/`, or `policy.yml` exist |
| `status` | Current lifecycle state if known from structured state |
| `current_plan` | Current plan filename if known |

## Step 3: activate with progressive disclosure

When the model or user activates an epic, load it in layers.

Recommended sequence:

1. `SKILL.md`
2. `EPIC.md`
3. `policy.yml` if present
4. `runtime/state/core.json` when present, otherwise `runtime/state.json`
5. the current plan in `runtime/plans/` when known
6. the 3-5 most recent entries in `runtime/log/`

Defer these until needed:

- `runtime/ROADMAP.md`
- `runtime/DECISIONS.md`
- older logs
- `references/`
- `skills/`
- `scripts/`
- `runtime/artifacts/`

For `spec_version: 0.5.2`, `SKILL.md` includes a standardized `## Agent Epics`
footer pinned by a canonical marker. Hosts should preserve that block exactly
and still treat `EPIC.md` plus `runtime/` as the authoritative resume surface.

Published epics may also include `metadata.source` in `SKILL.md` frontmatter
as an optional published-source hint. Hosts may use it to locate the full epic
when only `SKILL.md` is available, but trust policy should still govern any
fetch or install behavior.

## Step 4: let the agent maintain `runtime/`

Once activated, the agent should be able to create and update live operating
files in `runtime/`.

In practice, that means:

- create plans in `runtime/plans/`
- update `runtime/state.json` or files under `runtime/state/`
- append log entries in `runtime/log/`
- produce outputs in `runtime/artifacts/`
- read related references inside the epic when appropriate

## Step 5: resume correctly

When an epic is resumed in a later session, the harness should make it cheap
for the model to recover the current operating picture.

Minimum resume context:

- `EPIC.md`
- authoritative structured state
- current plan
- recent logs

Useful additional context when needed:

- `runtime/ROADMAP.md`
- `runtime/DECISIONS.md`
- specific artifacts referenced by the plan

## Step 6: add scripting support deliberately

If your harness supports runtime features, treat them as executable semantics,
not advisory prose.

That means:

- `policy.yml` is loaded and treated as a hard constraint
- `cron.d/` jobs are scheduled and invoked according to spec
- `hooks/` fire on supported trigger events
- unsupported scripting features are surfaced explicitly

## Support tiers

- **Catalog only**: discover epics and disclose them to the model
- **Interactive EPIC support**: discover, activate, resume, and persist
  `runtime/` updates
- **Full scripting support**: additionally execute hooks, cron jobs, and
  policy-constrained autonomous behavior
