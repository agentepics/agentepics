Epics fall into three broad archetypes. That is not just a filing decision. It
is how you decide what kind of durable system you are building.

A plain `SKILL.md` teaches an agent how to do something. An epic gives that
know-how a state container, a working memory, a history, and optional runtime
loops that can keep acting over time.

That means every archetype can do things a plain skill cannot:

- keep machine-readable state that survives across many sessions
- carry several concurrent operating loops around the same work
- accumulate decisions, artifacts, approvals, and logs
- react to events such as a meeting starting or a milestone changing
- run recurring work every day or every week without being re-explained

The archetypes differ in what stays stable and what changes:

- **Workflow epic**: the operating model stays stable while each run gets fresh `runtime/` state
- **Instance epic**: the project itself is unique, so the epic captures one evolving effort in a long-lived `runtime/`
- **Capability epic**: the epic stays installed and keeps operating as part of the agent, with persistent `runtime/` state

If you want the wider argument first, read
[Why state and reuse matter](/stateful-and-reusable). This page focuses on how
to recognize and structure each pattern.

## Workflow epic

A workflow epic is a **reusable operating model**. You keep the same process,
policies, references, hooks, and schedules, then run it again with new working
state for a new client, product, manuscript, or campaign.

This is what you want when the method should survive while the facts of the
current run change.

### Why a plain skill falls short

A skill can explain how to deliver a website. It cannot natively carry forward:

- which pages are approved for this client
- which launch blockers are still open
- what happened in the last client review
- which recurring checks should run every Friday
- what brief should be prepared automatically when the next review meeting starts

That is the difference between reusable know-how and a reusable operating
system.

### Example: client-website-delivery

This epic is reused for every new website project. The overall workflow stays
the same, but each client run gets its own `runtime/` tree with plans,
approvals, logs, and page state.

```directory
client-website-delivery/
├── SKILL.md
├── EPIC.md
├── runtime/
│   ├── ROADMAP.md
│   ├── DECISIONS.md
│   ├── plans/
│   │   ├── 001-discovery.md
│   │   ├── 002-design-approval.md
│   │   └── 003-launch-readiness.md
│   ├── state/
│   │   ├── core.json
│   │   ├── pages.json
│   │   ├── approvals.json
│   │   └── open-issues.json
│   ├── log/
│   │   ├── 2026-03-02T09-10-00Z-agent-audited-existing-site.md
│   │   ├── 2026-03-04T14-30-00Z-human-approved-sitemap.md
│   │   └── 2026-03-07T11-05-00Z-agent-updated-launch-checklist.md
│   └── artifacts/
│       ├── wireframes/
│       ├── copy/
│       └── exported-builds/
├── hooks/
│   ├── meeting-started.d/
│   │   └── 010-prepare-client-review-brief.md
│   └── milestone-complete.d/
│       └── 020-create-next-plan.md
├── cron.d/
│   └── weekly-seo-check.yml
├── policy.yml
└── references/
    ├── brand-guidelines.md
    └── competitor-notes.md
```

**What this buys you**

- `runtime/state/pages.json` can track each page as `draft`, `approved`, `blocked`, or
  `ready-to-ship`.
- `runtime/state/approvals.json` can record who approved homepage copy and when.
- `runtime/plans/003-launch-readiness.md` can become the current tactical loop for the
  next session.
- `cron.d/weekly-seo-check.yml` can keep the project healthy without a human
  remembering to ask.
- `hooks/meeting-started.d/010-prepare-client-review-brief.md` can assemble the
  latest sitemap, open issues, approvals, and launch blockers the moment a
  stakeholder meeting begins.

The point is not just that the website project lasts longer. The point is that
the epic becomes a reusable delivery system with durable memory and automation.

## Instance epic

An instance epic is a **one-off effort with unique scope**. The file set is not
meant to be reset and reused as a template for the exact same work. It is meant
to carry one real project all the way through.

This is what you want when the work accumulates too much context, too many
dependencies, and too many decisions to be treated as a sequence of isolated
sessions.

### Why a plain skill falls short

A skill can explain how film production works. It cannot keep the living state
of one actual feature film:

- which script draft is current
- which cast conversations are pending
- which locations are approved or at risk
- which financing assumptions are still valid
- which daily production checks must keep running
- what context should appear instantly when the morning production meeting starts

That needs a persistent operating context, not just a how-to guide.

### Example: feature-film

This epic holds the development, financing, preproduction, production, and
festival strategy for one specific film. It may run for months, with several
operating loops around the same shared state.

```directory
feature-film/
├── SKILL.md
├── EPIC.md
├── runtime/
│   ├── ROADMAP.md
│   ├── DECISIONS.md
│   ├── plans/
│   │   ├── 001-development.md
│   │   ├── 002-financing.md
│   │   ├── 003-preproduction.md
│   │   └── 004-festival-strategy.md
│   ├── state/
│   │   ├── core.json
│   │   ├── script.json
│   │   ├── budget.json
│   │   ├── casting.json
│   │   ├── locations.json
│   │   └── deliverables.json
│   ├── log/
│   │   ├── 2026-02-10T10-00-00Z-agent-updated-budget-scenarios.md
│   │   ├── 2026-02-14T16-20-00Z-human-approved-shooting-window.md
│   │   └── 2026-02-19T09-15-00Z-agent-created-preproduction-plan.md
│   └── artifacts/
│       ├── treatments/
│       ├── script-drafts/
│       ├── pitch-deck/
│       ├── schedules/
│       └── call-sheets/
├── hooks/
│   ├── meeting-started.d/
│   │   └── 010-prepare-production-brief.md
│   └── status-changed.d/
│       └── 020-log-transition.md
├── cron.d/
│   ├── daily-shoot-readiness.yml
│   └── weekly-deadline-review.yml
├── policy.yml
└── references/
    ├── comps.md
    ├── union-rules.md
    └── location-constraints.md
```

**What this buys you**

- `runtime/state/script.json` can track draft number, locked scenes, rewrite
  priorities, and outstanding notes.
- `runtime/state/budget.json` can hold financing assumptions, approved ceilings, and
  what changed after each investor conversation.
- `runtime/state/locations.json` can record scouting status, permit risk, and fallback
  options.
- `cron.d/daily-shoot-readiness.yml` can check tomorrow's blockers every day
  during production.
- `hooks/meeting-started.d/010-prepare-production-brief.md` can open the right
  summary for a financing meeting, casting review, or preproduction check-in.

This is where epics stop looking like long tasks and start looking like living
containers for serious work.

## Capability epic

A capability epic extends the **agent itself**. It is not mainly something to
finish. It is something to install, constrain, maintain, and let operate over
time.

This is what you want when the agent should keep a durable service in place:
memory, monitoring, briefing, ingestion, triage, or some other standing
capability.

### Why a plain skill falls short

A skill can explain how to prepare a meeting brief. It cannot stay installed as
the system that:

- scans the calendar every morning
- keeps structured state on upcoming meetings and owners
- prepares briefs automatically when a meeting starts
- records decisions and follow-ups after the meeting ends
- keeps improving the briefing process over time under policy

That is an installed operating capability, not a one-shot instruction set.

### Example: meeting-briefing-system

This epic stays installed across the workspace. It continuously tracks upcoming
meetings, prepares context packs, and updates durable meeting state over time.

```directory
meeting-briefing-system/
├── SKILL.md
├── EPIC.md
├── runtime/
│   ├── plans/
│   │   └── 001-maintenance-and-improvements.md
│   ├── state/
│   │   ├── core.json
│   │   ├── meetings.json
│   │   ├── contacts.json
│   │   └── commitments.json
│   ├── log/
│   │   ├── 2026-03-01T07-00-00Z-agent-scanned-upcoming-calendar.md
│   │   ├── 2026-03-01T08-55-00Z-agent-prepared-product-review-brief.md
│   │   └── 2026-03-01T10-30-00Z-agent-recorded-follow-ups.md
│   └── artifacts/
│       └── briefs/
├── hooks/
│   ├── meeting-started.d/
│   │   └── 010-assemble-brief.md
│   └── status-changed.d/
│       └── 020-log-health-transition.md
├── cron.d/
│   ├── daily-calendar-scan.yml
│   └── nightly-followup-audit.yml
├── policy.yml
├── scripts/
│   ├── fetch_calendar.py
│   └── assemble_brief.py
└── references/
    └── briefing-template.md
```

**What this buys you**

- `cron.d/daily-calendar-scan.yml` can look ahead and update `runtime/state/meetings.json`
  before anyone asks.
- `hooks/meeting-started.d/010-assemble-brief.md` can prepare the current
  agenda, relevant decisions, open commitments, and stakeholder context as the
  meeting begins.
- `runtime/state/commitments.json` can preserve promises made in prior meetings so the
  system does not lose track of them next week.
- `runtime/plans/001-maintenance-and-improvements.md` can hold work to improve the
  capability itself without confusing that with user-facing meeting operations.

This is the archetype that makes it obvious an epic can be a permanent agent
surface, not just a project folder.

## Choosing an archetype

| Question | Workflow | Instance | Capability |
|----------|----------|----------|------------|
| What stays stable? | The operating model | The project identity | The installed service |
| What changes over time? | Per-run state and artifacts | Nearly everything inside the project | Operational state, logs, and maintenance plans |
| Will it be reused? | Yes, for many runs | No, it is one real effort | Yes, as a standing capability |
| Does it finish? | Each run does | Usually yes | Rarely |
| Typical operating loops | Plans, approvals, recurring checks, review hooks | Plans, deadlines, meeting hooks, production checks | Cron jobs, event hooks, durable service state |
| Best mental model | A reusable operating procedure | A living project container | An installed subsystem for the agent |

These are patterns, not rigid categories. A website program may blend workflow
and capability traits. A large project may start as an instance epic and later
spin out a reusable workflow epic.

The important decision is not which label sounds best. It is which structure
best captures the durable state, recurring behavior, and reusable operating
surface your agent actually needs.
