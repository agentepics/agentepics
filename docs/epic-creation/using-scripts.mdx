Epics can instruct agents to run commands directly and can also bundle reusable
scripts in `scripts/`. The important design choice is not the language. It is
how much reliability and reuse the task needs.

## Choose the lightest option that works

Use a one-off command when:

- an existing tool already does the job
- the command is short and stable
- you do not expect to reuse the logic much

Bundle a script when:

- the command is getting hard to remember or easy to get wrong
- the same operation will be reused across phases or runs
- you need clear inputs, outputs, and error handling
- you want to pin behavior more tightly over time

## One-off commands

When an existing package already does what you need, reference it directly in
`SKILL.md`, `EPIC.md`, or a phase description.

Examples:

```bash
uvx ruff@0.8.0 check .
npx eslint@9 --fix .
go run golang.org/x/tools/cmd/goimports@v0.28.0 .
```

Guidelines:

- pin versions when reproducibility matters
- state prerequisites in the epic instructions
- move complex commands into scripts before they become fragile

## Referencing bundled scripts

Reference bundled scripts with paths relative to the epic root.

```markdown EPIC.md
## Available scripts

- `scripts/validate.sh` - validates configuration files
- `scripts/process.py` - processes input data
```

Then call them from the phase or plan that needs them.

## Designing scripts for agents

Good agent-facing scripts share a few traits:

- they do one clear job
- they accept explicit arguments
- they avoid interactive prompts
- they print structured, machine-parseable output when possible
- they fail with helpful error messages

## Self-contained scripts

When reusable logic needs dependencies, prefer self-contained scripts that
declare what they need inline.

Examples of good fits:

- Python scripts run with `uv run`
- Deno scripts with direct imports
- shell scripts with clear environment assumptions

The goal is simple invocation, not a large setup ritual.

## Practical advice

- use scripts for reliability, not because scripts feel more "serious"
- keep commands and scripts close to the phase where they matter
- document the purpose of each bundled script where the agent will see it
- prefer a few trustworthy scripts over a long toolbox the agent never uses
