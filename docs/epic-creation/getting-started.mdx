This guide is about **authoring an epic definition**.

It is not about runtime operation yet. At creation time, the goal is to define
something reusable and intelligible: what the epic is for, when it activates,
how it is structured, what phases it moves through, and what tools or supporting
skills each phase depends on.

An epic becomes powerful later because it can hold durable state and runtime
behavior. But first it needs a good operating definition.

If you want the motivation, read
[Why state and reuse matter](/stateful-and-reusable). If you want the
operational side, read [Epic Usage](/epic-usage).

## What you are creating

At minimum, an epic is:

- a valid `SKILL.md` package for discovery and activation
- an `EPIC.md` file that defines the workflow or capability itself

Those two files hold the reusable part of the epic. They should describe what
stays stable across runs, not the transient details of one session.

```directory
saas-launch/
├── SKILL.md
└── EPIC.md
```

## Step 1: Write `SKILL.md` for activation

`SKILL.md` tells an agent when this epic is relevant and why it should load it.
In `0.5.2`, keep the top section short and activation-cheap, then append the
canonical `## Agent Epics` footer.

```mdx
---
name: saas-launch
description: >
  Workflow for launching a SaaS product. Activate this epic when planning
  or executing a new product launch.
metadata:
  source:
    repo: github.com/agentepics/epics
    path: saas-launch
    ref: main
---

# SaaS Launch

## When to activate
Use this epic when the work is about launching a SaaS product.

## What it helps with
- defining the launch phases
- coordinating supporting work
- keeping the operating model reusable across launches

See the **Agent Epics** section below if this is your first encounter with the Agent Epics system.

## Agent Epics
<!-- epics-canonical-footer: https://raw.githubusercontent.com/agentepics/agentepics/refs/heads/main/footer.md -->
...
```

Write `SKILL.md` to be:

- specific enough that the agent activates it at the right time
- general enough that it still works across multiple runs or instances
- short enough that activation stays cheap
- clear that durable operating context lives in `EPIC.md`

The `name` field must use Unicode lowercase letters, digits, and hyphens,
match the directory name, and stay under 64 characters.

For published epics, `metadata.source` is recommended but not required in the
frontmatter. Use it when you want hosts that encounter a standalone `SKILL.md`
to have a machine-readable hint for where the full epic was published. The
recommended form is:

```yaml
metadata:
  source:
    repo: github.com/agentepics/epics
    path: saas-launch
    ref: main
```

## Step 2: Write `EPIC.md` for the durable definition

`EPIC.md` is where the real epic starts. It defines the purpose, scope, phases,
success criteria, and resumption model.

```mdx
---
spec_version: 0.5.2
id: saas-launch
tags: [saas, launch, product]
timezone: UTC
---

# SaaS Launch

## Purpose
Take a product from architecture to first paying customer.

## Scope
This epic covers launch planning, implementation coordination, beta readiness,
launch readiness, and early customer onboarding.

## Success Criteria
- Launch to first real users
- Reach first paying customer
- Keep the launch process reusable for future products

## Resume
Review the current phase, active plan, and recent history before continuing.
```

The body should stay durable. Write what remains true across sessions and, for
workflow epics, across runs.

## Step 3: Write strong phase descriptions

The most important authoring work is usually not the frontmatter. It is the
phase design.

Bad phase descriptions are vague labels:

- “build product”
- “launch”
- “marketing”

Strong phase descriptions tell the agent:

- what this phase is trying to achieve
- what inputs it depends on
- what skills, scripts, or references it should consult
- what decisions are expected here
- what counts as done
- what should happen next

For example:

```markdown
## Phases

### 1. Architecture decisions
Choose the core system shape for the product. Evaluate database, API, auth, and
deployment architecture. Use the architecture review skill and relevant
references before locking decisions.

Exit criteria:
- primary database selected
- API shape documented
- deployment approach chosen

### 2. Core implementation
Build the minimum production path for the product. Use the backend and frontend
implementation skills, follow the architecture decisions already made, and keep
open questions visible.

Exit criteria:
- core product flow works end to end
- release blockers are known

### 3. Beta readiness
Prepare onboarding, support, analytics, and feedback loops for first external
users.

Exit criteria:
- beta cohort defined
- onboarding flow documented
- feedback collection path ready
```

That level of specificity is what turns an epic into an operating model rather
than a folder with nice filenames.

## Step 4: Attach the right supporting material to each phase

An epic gets much stronger when each phase has the support it actually needs.

Common supports:

- `references/` for durable source material
- `skills/` for epic-scoped helper skills
- `scripts/` for deterministic checks or data collection
- `runtime/artifacts/` for outputs the epic is expected to produce during a run

```directory
saas-launch/
├── SKILL.md
├── EPIC.md
├── runtime/
│   └── artifacts/
│       ├── launch-briefs/
│       └── reports/
├── references/
│   ├── launch-checklist.md
│   ├── pricing-notes.md
│   └── onboarding-requirements.md
├── skills/
│   ├── architecture-review/
│   │   └── SKILL.md
│   └── beta-feedback-triage/
│       └── SKILL.md
├── scripts/
│   ├── fetch_metrics.py
│   └── validate_release_readiness.sh
```

Think in phase terms:

- architecture phase may need `references/architecture-principles.md` and a
  helper skill for tradeoff analysis
- beta phase may need a script to fetch metrics and a skill for feedback triage
- launch phase may need checklists, release scripts, and artifact output paths

Do not dump everything into the epic at once. Add the supports that materially
improve the workflow definition.

## Step 5: Decide what is reusable and what is instance-specific

This is the central authoring question.

For a **workflow epic**, the reusable part is the method:

- phases
- policies
- references
- helper skills
- scripts
- success model

For an **instance epic**, more of the definition is specific to one project:

- stakeholders
- deadlines
- deliverables
- constraints

For a **capability epic**, the reusable part is the installed service model:

- what the capability does
- when it activates
- what it can operate on
- what it must never do

See [Epic archetypes](/epic-creation/archetypes) for concrete examples of each.

## Step 6: Use this authoring checklist

Before you call the epic “created,” check:

- Does `SKILL.md` clearly say when this epic should activate?
- Does `EPIC.md` clearly define purpose, scope, success, and resume behavior?
- Are the phases concrete enough that an agent knows what good work looks like?
- Does each major phase point to the right references, skills, or scripts?
- Is the reusable operating model clear, or is it muddied with one-off session details?

If the answer to those questions is yes, you have authored an epic definition.

## What comes next

Once the epic exists, you can start **using** it:

- add `plans/` when the epic needs a tactical working loop
- add `state.json` or `state/` when the epic needs machine-readable facts
- add `log/` when continuity across sessions matters
- add `hooks/`, `cron.d/`, and `policy.yml` when the epic becomes an operating surface

That is the next layer, and it belongs on a separate page.
