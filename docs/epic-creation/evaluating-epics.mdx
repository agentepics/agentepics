This guide is about answering a practical question: does the epic actually work
reliably, not just once, but across activation, execution, resumption, and
ongoing use?

## The evaluation loop

Use a short, repeatable loop:

1. define 2-3 realistic tasks
2. run them with the epic
3. run them without the epic, or against the previous version
4. grade outputs and state changes
5. adjust the epic
6. rerun

## What to evaluate

For epics, output quality is only part of the story. Also check whether:

- the epic activates for the right tasks
- the agent follows the intended phases
- plans and state evolve coherently
- resumption uses the right sources of truth
- scripting behavior does what the epic promises, if scripting is supported

## Designing test cases

A test case has three parts:

- **Prompt**: a realistic user message
- **Expected output**: a human-readable description of success
- **Input files**: optional files the epic needs

Store test cases in `evals/evals.json` inside your epic directory:

```json evals/evals.json
{
  "epic_id": "saas-launch",
  "evals": [
    {
      "id": 1,
      "prompt": "We are preparing the beta launch for our SaaS product. Can you review what still blocks beta readiness and move the plan forward?",
      "expected_output": "The epic is activated, the current phase is respected, the plan is updated coherently, and the output identifies the real beta blockers.",
      "files": ["evals/files/launch-brief.md"]
    }
  ]
}
```

## Running evals

Run each case twice:

- once **with the epic**
- once **without the epic**, or with the previous epic version

That gives you a baseline instead of relying on intuition.

### Recommended workspace shape

```text
saas-launch-workspace/
└── iteration-1/
    ├── eval-beta-readiness/
    │   ├── with_epic/
    │   │   ├── outputs/
    │   │   ├── timing.json
    │   │   └── grading.json
    │   └── without_epic/
    │       ├── outputs/
    │       ├── timing.json
    │       └── grading.json
    └── benchmark.json
```

## Writing assertions

Prefer assertions that are specific and observable:

- the epic activated
- the current phase was respected
- the correct state source was loaded
- the plan was updated coherently
- a new log entry was produced when expected
- the output has the required structure

Avoid brittle assertions that depend on one exact phrasing unless wording is
part of the requirement.

## Grading outputs

Use two layers:

- **Objective checks** for structure, files, state updates, and plan changes
- **Human review** for writing quality, design quality, or whether the overall
  operating model still feels sound

Not everything should become an assertion.

## Tracking cost and speed

Also record:

- total tokens
- duration
- failure modes

An epic may cost more than the baseline and still be worth it if resumption,
state handling, and output quality improve enough. Measure the tradeoff
explicitly instead of guessing.

## Reviewing results

After one iteration, look for patterns:

- Where did the epic fail to activate?
- Where did the agent read the wrong file first?
- Which parts of the phase design were too vague?
- Which instructions belonged in structured state or scripts instead of prose?

That gives you the next set of edits.
