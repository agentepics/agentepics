This guide covers the `0.5.1` to `0.5.2` packaging change.

In `0.5.2`, `SKILL.md` becomes a dual-purpose entrypoint:

- the top of the file remains the normal skill discovery and activation surface
- the bottom of the file adds a standardized `## Agent Epics` footer
- `EPIC.md` remains authoritative for lifecycle, state model, guardrails, and resume behavior

The `runtime/` layout from `0.5.1` does not move in `0.5.2`.

## For epic authors

### What changes

Keep `SKILL.md` short and activation-cheap, but split it into two sections:

1. A standard skill surface with normal `SKILL.md` frontmatter (`name`,
   `description`, and any optional standard skill fields).
2. A canonical `## Agent Epics` footer with the marker:

```html
<!-- epics-canonical-footer: https://raw.githubusercontent.com/agentepics/agentepics/refs/heads/main/footer.md -->
```

The top section should:

- say what the epic does
- say when to activate it
- say that durable operating context lives in `EPIC.md`
- include a one-line pointer near the top such as `See the **Agent Epics** section below if this is your first encounter with the Agent Epics system.`

The top section should not duplicate `EPIC.md`. Resume detail, lifecycle,
state rules, and guardrails stay authoritative in `EPIC.md` and `runtime/`.

### Upgrade steps

1. Set `EPIC.md.spec_version` to `0.5.2`.
2. Add standard skill frontmatter to `SKILL.md` if it is missing.
3. For published epics, consider adding `metadata.source` to `SKILL.md`
   frontmatter as a published-source hint. It is recommended, not required.
4. Replace long self-contained resume prose in `SKILL.md` with a short
   activation-oriented top section that points to `EPIC.md`.
5. Append the canonical footer from [`footer.md`](https://github.com/agentepics/agentepics/blob/v0.5.2/footer.md).
6. Keep all live plans, state, logs, roadmap, decisions, and artifacts under
   `runtime/` exactly as in `0.5.1`.
7. Validate the package and refresh stale footers through tooling rather than
   by forking the footer text by hand.

<Note>
Use `footer.md` as the source text when upgrading. The footer marker embedded in `SKILL.md` uses the canonical raw URL on `refs/heads/main`; do not copy the GitHub blob URL from this migration guide into the marker.
</Note>

### Author checklist

- `EPIC.md` says `spec_version: 0.5.2`
- `SKILL.md` starts with standard skill frontmatter
- published epics should include `metadata.source` in `SKILL.md` frontmatter
  when they want hosts to have a recovery hint from standalone `SKILL.md`
- `SKILL.md` mentions that durable context lives in `EPIC.md`
- `SKILL.md` includes the canonical `## Agent Epics` footer and marker
- runtime behavior still lives in `EPIC.md`, `runtime/`, `hooks/`, `cron.d/`,
  and `policy.yml`, not in duplicated `SKILL.md` prose

## For host coders

### What changes

Hosts should treat `0.5.2` as:

- the same `runtime/` filesystem layout as `0.5.1`
- a stricter `SKILL.md` contract for authored epics
- a portable footer that hosts may parse, preserve, diff, and project into
  host-native integration surfaces

The footer is not a replacement for `EPIC.md`. It is a compact bridge for
discovery, orientation, and capability fallback.

### Required behavior changes

Update activation and resumption logic to:

1. Read `SKILL.md` frontmatter as ordinary skill metadata.
2. Read the short operational top section of `SKILL.md`.
3. Preserve and understand the canonical `## Agent Epics` footer when present.
4. Continue with `EPIC.md`, `runtime/state*`, `runtime/plans/`, and
   `runtime/log/` as the authoritative resumption sequence.
5. If `metadata.source` is present, treat it as a published-source hint when
   only `SKILL.md` is available. Support both an absolute `http`/`https` URL
   string and a structured object with `repo`, `path`, and optional `ref`.
   Trust policy still governs whether fetching or installing is allowed.
6. If the host lacks epic support, surface the canonical installer or
   integration path (`https://epics.sh`) but do not auto-install on behalf of a
   repo-local epic unless trust policy explicitly allows it.

### Compatibility strategy

During migration:

- treat `0.5.1` epics as valid footer-less epics
- treat `0.5.2` epics as requiring the canonical footer when you validate or
  scaffold authored packages
- ignore unknown future footer details you do not understand unless they change
  execution semantics in a way you cannot safely support
- preserve the footer block exactly when copying, installing, exporting, or
  rewriting `SKILL.md`

### Host checklist

- `runtime/` handling stays identical to `0.5.1`
- `SKILL.md` frontmatter remains the skill discovery surface
- `## Agent Epics` is parsed opportunistically and preserved exactly
- `EPIC.md` remains the authoritative lifecycle and state document
- hosts do not silently self-bootstrap runtime support from untrusted repo-local epics

## Notes

- `0.5.2` is a compatibility and packaging revision, not a runtime-tree move
- the canonical footer is versioned so tooling can detect stale copies
- authors should refresh the footer through tooling when the spec revision changes
