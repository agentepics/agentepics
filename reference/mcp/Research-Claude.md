# MCP under the microscope: what builders actually think

**Anthropic's Model Context Protocol has become the de facto standard for connecting AI agents to external tools and data — but its rapid adoption has outpaced its security model, architectural maturity, and the question of whether structured protocols even make sense for systems that understand natural language.** After 16 months in the wild, MCP boasts **97 million monthly SDK downloads**, support from every major AI lab, and a new home at the Linux Foundation. Yet practitioners who have built with it report a protocol caught between genuine standardization value and fundamental design tensions that no amount of iteration may resolve. This report synthesizes criticism and praise from engineers, security researchers, framework authors, and AI practitioners who have hands-on experience with MCP — drawn from Hacker News threads, engineering blogs, GitHub discussions, security research papers, and expert commentary.

## What MCP is and why it exists

MCP launched in November 2024 as an open protocol enabling AI models to interact with external tools, data sources, and services through a standardized interface. Built on **JSON-RPC 2.0**, it defines three core primitives — Tools (executable functions), Resources (data sources), and Prompts (templated interactions) — that MCP servers expose to AI clients like Claude, ChatGPT, Cursor, or VS Code.

The core pitch is solving the **N×M integration problem**. Without MCP, every AI application must build custom integrations for every tool — N clients multiplied by M tools equals N×M implementations. MCP reduces this to N+M: build one MCP server for your tool, and every compliant client can use it. Justin Spahr-Summers, MCP co-creator at Anthropic, described the intent: "We definitely hope this will solve the NxM problem." The commonly invoked analogy compares MCP to USB-C for AI or, more precisely, to the **Language Server Protocol (LSP)** that standardized how IDEs interact with programming language tooling.

The protocol has evolved through four major specification releases. It launched with no authentication model and two transport mechanisms (stdio for local servers and HTTP+SSE for remote). By March 2025, it gained OAuth 2.1 authorization and a new Streamable HTTP transport. The June 2025 release hardened security and deprecated the original SSE transport. The November 2025 anniversary release added experimental async tasks, an extensions framework, and enterprise authorization improvements. In December 2025, Anthropic donated MCP to the **Agentic AI Foundation (AAIF)** under the Linux Foundation, co-founded with Block and OpenAI, with platinum members including Amazon, Google, Microsoft, Bloomberg, and Cloudflare.

Adoption metrics are significant: the GitHub servers repository has **~77,700 stars**, over **10,000 active MCP servers** exist in the ecosystem, and the protocol is supported by ChatGPT, Claude, Gemini, Cursor, VS Code, and Microsoft Copilot. Block reports deploying **60+ internal MCP servers** with **50–75% time savings** on integration work.

## The real strengths practitioners identify

The most credible praise for MCP centers on three concrete benefits that alternatives struggle to replicate.

**Provider-agnostic tool portability** is MCP's clearest win. A single MCP server works across Claude, ChatGPT, Gemini, and any other compliant client without modification. Direct function calling, by contrast, uses vendor-specific schemas — OpenAI, Anthropic, and Google each define tool interfaces differently. Harrison Chase, CEO of LangChain, captures the key insight: "MCP is useful when you want to bring tools to an agent you don't control." For developers building agents they fully control, function calling works fine. But for tool publishers, platform builders, and non-developers wanting to extend existing AI assistants, MCP provides genuine value. Chase likens the long-tail opportunity to Zapier — connecting services for users who can't write custom integrations.

**Ecosystem convergence** has created a powerful network effect. When Google's Demis Hassabis announced Gemini would support MCP, calling it "a good protocol rapidly becoming an open standard," it signaled something rare in AI infrastructure: cross-vendor agreement. Bloomberg CTO Shawn Edwards called MCP "a foundational building block for APIs in the era of agentic AI." The AAIF governance structure further reduces vendor lock-in concerns. As one Hacker News commenter noted, "When Anthropic, OpenAI, Google, and Microsoft all support the same integration standard, that's not hype — that's infrastructure."

**The thin abstraction design** also earns praise from implementers who appreciate what MCP doesn't try to do. It doesn't impose agent architectures, orchestration patterns, or runtime constraints. As one HN commenter put it: "MCP is just a small, boring protocol that lets agents call tools in a standard way, nothing more. The real value is that MCP stays out of your way." The protocol's LSP-inspired design was specifically praised by early reviewers — one called reading the specification "a delight, with so many tasteful little decisions."

The community's openness to feedback has also been recognized. Den Delimarsky, who coordinated the MCP auth RFC while at Microsoft, commended Anthropic: "The protocol is in very early stages and there are a lot of things that still need to be figured out. That said, I can commend Anthropic on being very open to listening to the community. The authorization spec RFC is a coordinated effort between security experts at Microsoft, Arcade, Hellō, Auth0/Okta, Stytch, Descope, and quite a few others."

## Security is the elephant in every room

The most damning criticism of MCP comes from security researchers who have demonstrated not theoretical risks but working exploits against production MCP clients.

**Tool poisoning attacks**, discovered by Invariant Labs (Luca Beurer-Kellner and Marc Fischer), represent the protocol's most fundamental security challenge. Malicious instructions embedded in MCP tool descriptions are invisible to users but fully processed by LLMs. In a demonstrated attack against Cursor IDE, a seemingly innocent `add` tool contained hidden `<IMPORTANT>` tags instructing the model to read `~/.cursor/mcp.json` (which stores credentials for other MCP servers) and `~/.ssh/id_rsa`, then exfiltrate the data via a hidden parameter. Cursor's confirmation dialog showed only a simplified tool name — the full malicious arguments were hidden behind the UI. CyberArk Labs extended this to **"Full-Schema Poisoning"** — injecting instructions into type fields, required arrays, non-standard JSON schema fields, and even tool outputs, making static detection nearly impossible.

The problem compounds with **cross-server shadowing**. When multiple MCP servers are connected to the same client, a malicious server can inject tool descriptions that hijack the agent's behavior with respect to *trusted* servers. Invariant demonstrated a scenario where a malicious "add" tool from one server contained hidden instructions to redirect all emails sent via a trusted email server to an attacker's address — and the agent complied silently. Security researcher wunderwuzzi (Embrace The Red blog) went further, demonstrating that **hidden Unicode Tag characters** embedded in tool metadata — invisible when users inspect the UI — are executed by Claude. He responsibly disclosed this to Anthropic over 14 months before publishing, and "it was not seen as a security vulnerability." His blunt assessment: MCP should be called "Model *Control* Protocol" because "due to prompt injection, MCP tool servers control the client."

Real-world incidents have validated these concerns. A timeline compiled by AuthZed documents: **CVE-2025-6514**, a critical command-injection vulnerability in `mcp-remote` (437,000+ downloads) enabling remote code execution; three vulnerabilities in Anthropic's own reference MCP Git server; the first malicious MCP server in the wild ("postmark-mcp" npm package stealing emails via BCC); **~1,000 MCP servers found exposed online with zero authorization** by Bitsight TRACE; and a trojanized Oura MCP server delivering the StealC infostealer. Obsidian Security discovered OAuth account takeover vulnerabilities in production MCP deployments affecting "well-known organizations," where the protocol's double-token architecture allowed CSRF-style attacks.

The core issue, as HN commenter wat10000 articulated, is that "the fact that all LLM input gets treated equally seems like a critical flaw that must be fixed before LLMs can be given control over anything privileged. The LLM needs an ironclad distinction between 'this is input from the user' and 'this is input from the outside that must not be obeyed.'" This is not an MCP-specific problem — it's inherent to LLM architectures — but MCP dramatically amplifies the attack surface by making it trivially easy to connect untrusted tool servers to privileged AI systems.

## Context bloat and the composability problem

Beyond security, the most technically substantive criticism targets MCP's interaction with LLM context windows — a limitation many practitioners consider **architecturally fundamental rather than fixable**.

Every MCP tool's schema and description consumes tokens in the model's context before any useful work begins. Mario Zechner measured the cost: the **Playwright MCP server exposes 21 tools consuming 13,700 tokens** (6.8% of a 200K context window), while the **Chrome DevTools MCP server uses 26 tools at 18,000 tokens** (9%). His alternative — simple CLI scripts with a README — achieved the same browser automation capability in **225 tokens**. As HN commenter noodletheworld argued: "MCP does not scale. It *cannot* scale beyond a certain threshold. It is *impossible* to add an unlimited number of tools to your agent's context without negatively impacting capability. This is fundamentally different from installing a package in any normal package system, where *not interfering* is a fundamental property."

Tom Bedor, author of the widely-discussed "MCP is a fad" post, quantified the practical constraint: "OpenAI recommends keeping tools well below 20, yet many MCP servers exceed this threshold individually." When multiple servers are connected, tools interfere with each other and degrade model performance.

MCP also lacks **composability** — data returned by one tool must pass through the model's context to reach another tool. There are no variables, no piping between tools without LLM mediation. This multiplies token costs and increases error rates for large data transfers. Anthropic implicitly acknowledged this problem in November 2025 when they published a blog post demonstrating that having agents **write code to call tools** (rather than using MCP's tool-calling protocol) reduced token usage from **150,000 tokens to 2,000 — a 98.7% reduction**. Daniel Miessler, creator of the Fabric AI framework, interpreted this as "massive shade at MCPs, and basically deprecated them down to being like service directories." Steve Krouse (Val Town founder) captured the irony: "We started with OpenAPI specs, abandoned them for MCP because LLMs couldn't handle them, and now that LLMs can handle specs again, we're generating specs from MCP. We've gone full circle."

Notably, Simon Willison — one of MCP's most thoughtful critics — acknowledged in January 2026 that Claude Code's new **MCP Tool Search** feature, which loads tool schemas on-demand rather than all at once, largely resolves the context pollution issue: "Context pollution is why I rarely used MCP. Now that it's solved, there's no reason not to hook up dozens or even hundreds of MCPs to Claude Code."

## The stateful design and enterprise authorization headaches

MCP's **stateful protocol design** has emerged as a significant architectural concern, officially acknowledged by the MCP Transport Working Group in December 2025. Stateful connections force "sticky" routing that pins traffic to specific servers, preventing effective auto-scaling. Load balancers must parse full JSON-RPC payloads to route traffic instead of using standard HTTP patterns. Developers building simple, ephemeral tools must manage complex backend storage for basic interactions. The Transport Working Group is working toward making MCP stateless by replacing the `initialize` handshake with per-request metadata, targeting a **June 2026 spec release** — but this represents a fundamental redesign 18 months after launch.

The OAuth authorization specification has drawn particularly fierce criticism from enterprise security practitioners. Christian Posta characterized it as "a mess for enterprise," noting that the spec originally required every MCP server to act as its own authorization server — a pattern fundamentally at odds with enterprises that use centralized identity providers like Okta or Auth0. Dick Hardt, co-author of the OAuth 2.1 spec itself, called MCP's approach "a novel usage of OAuth that differs significantly from traditional patterns." The spec's reliance on **Dynamic Client Registration (DCR)** — which most enterprise OAuth providers don't support and security teams won't allow anonymously — created further friction. Aaron Parecki, another OAuth spec co-author, identified a "Shadow IT" problem: enterprise IdPs only see users logging into SaaS services, not the MCP connections established between AI clients and those services, leaving IT administrators blind to actual access patterns.

The November 2025 spec release introduced **Client ID Metadata Documents** (replacing DCR) and **Cross App Access (XAA)** for enterprise-managed authorization, but adoption remains nascent and the enterprise auth story continues to evolve.

## How MCP compares to the alternatives

**Against OpenAPI/Swagger**, MCP's defenders argue that OpenAPI *describes* existing APIs while MCP *prescribes* a uniform calling convention. As Glama.ai's analysis noted, "MCP mandates specific patterns: JSON-RPC 2.0 transport, single input schema per tool, deterministic execution." OpenAPI documents thousands of inconsistent API designs; MCP enforces one pattern that models learn once. Critics counter that LLMs are increasingly capable of reading OpenAPI specs and writing API calls directly — and multiple tools now generate MCP servers from OpenAPI specs automatically, suggesting the two layers may be converging rather than competing.

**Against direct function calling**, MCP adds a process boundary and server management overhead that function calling avoids. Tom Bedor noted: "Each MCP server starts a separate process that survives for the length of the agent session. Even in the healthy state, this introduces a collection of mostly-idle processes." For developers building agents they control, function calling is simpler and more direct. MCP's advantage emerges only when tools need to be portable across multiple AI platforms.

**Against CLI tools**, practitioners like Peter Steinberger (founder of PSPDFKit) and Simon Willison have argued that for coding agents, CLIs are strictly superior: "I can just refer to a CLI by name. I don't need any explanation in my agents file. I don't have to pay a price for any tools, unlike MCPs which are a constant cost." Armin Ronacher (creator of Flask) went further: "My agent writes its own glue code so the benefit does not seem to really exist in practice. Every time I think I have a use case for MCP, I discover that when I ask the agent to just write its own skill, it works better."

**Against Google's A2A (Agent-to-Agent) protocol**, the consensus is clear: they are **complementary, not competitive**. MCP handles vertical integration (connecting models to tools), while A2A handles horizontal integration (enabling agents to collaborate with each other). Google explicitly positioned A2A alongside MCP in documentation titled "A2A ❤️ MCP." Both protocols now reside under the Linux Foundation. IBM's ACP (Agent Communication Protocol) occupies similar agent-to-agent territory with additional built-in memory and human-in-the-loop capabilities.

## How MCP has evolved and whether criticisms are being addressed

The protocol's evolution reveals a pattern: **launch fast, iterate on community feedback, and progressively address the most vocal criticisms** — though some fundamental issues remain unresolved.

| Criticism | Status | Response |
|-----------|--------|----------|
| No authentication | ✅ Addressed | OAuth 2.1 added March 2025 |
| HTTP+SSE limitations | ✅ Addressed | Streamable HTTP replaced SSE |
| No async operations | ✅ Addressed | Tasks primitive added Nov 2025 |
| Vendor lock-in | ✅ Addressed | Donated to Linux Foundation |
| No server discovery | ✅ Addressed | MCP Registry launched Sep 2025 |
| Enterprise auth patterns | 🟡 Improving | Client ID metadata, XAA, but still evolving |
| Stateful scaling problems | 🟡 In progress | Stateless redesign targeting June 2026 |
| Security vulnerabilities | 🟡 Ongoing | Tool annotations, best practices page; prompt injection remains inherent |
| Context window bloat | 🟡 Partial | Tool Search helps; fundamental token cost remains |
| Composability | ❌ Unresolved | No protocol-level solution; code execution workaround |

The governance transition has drawn mixed reactions. Moncef Abboud questioned whether MCP is mature enough for foundation governance: "I would have much preferred for Anthropic and a small strike team of engaged developers to move fast and fix a lot of the issues." Others see the AAIF as essential for legitimacy — preventing any single company from controlling the standard.

Nuno Campos, LangGraph lead at LangChain, offered perhaps the most measured skepticism about MCP's long-term ceiling: "I think you're underestimating the degree to which the rest of the agent needs to be tailored to the tools you give it access to. Honestly, I think Zapier is the upper bound on MCP potential." Harrison Chase disagreed, seeing a future of one-click MCP app installation — but both acknowledged that the protocol's current form factor "sucks."

## Conclusion: a useful standard with fundamental tensions

MCP has achieved something rare and genuinely valuable: cross-vendor consensus on an integration protocol in a fast-moving field. Its network effects are real, its adoption is substantial, and the problems it solves — tool portability, dynamic discovery, and the N×M integration burden — are legitimate. For tool publishers, platform builders, and non-developers extending AI assistants, nothing else currently offers comparable reach.

But the protocol faces tensions that iteration alone may not resolve. **The security model is retrofitted onto a trust architecture that fundamentally assumes benign actors** — and the gap between what users see and what LLMs process creates an attack surface that tool annotations and best-practice documents cannot close. **Context window consumption is an architectural tax** that grows with every connected server, though on-demand tool loading (like Claude Code's Tool Search) offers a partial escape valve. **The philosophical question — whether AI agents that understand natural language need structured protocols at all — remains genuinely open.** As models improve at reading documentation and writing their own integration code, MCP's value proposition narrows toward use cases where the user doesn't control the agent.

The most likely outcome is not that MCP dies or triumphs unconditionally, but that it **settles into a specific niche**: the standard interface layer for tool publishers who want maximum distribution across AI platforms, coexisting with CLI tools, code-generation approaches, and direct function calling for developers who build and control their own agents. Whether that niche justifies the "USB-C for AI" aspiration remains the open question — one that the next year of production usage, not protocol committee deliberation, will answer.
